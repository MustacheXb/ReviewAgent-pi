## 1. 背景与目的

ReviewAgent 是一套基于 LLM 的代码评审实验系统（下称「本系统」），计划部署于企业内并接入企业内部模型网关（下称「网关」）。本文档基于一次受控对照实验的实测结论，提出网关侧需满足的功能与计量要求，作为网关建设/优化的需求基线与验收依据。

### 1.1 实验结论摘要（详见分析报告 §4/§5）

本系统此前分别通过 **DeepSeek 官方 API**（基准直连）与**火山引擎网关**（真实网关实现样例）完成同一受控矩阵：同模型 id `deepseek-v4-flash`、3 case × 5 配置 × 3 重复 = 45 单元，请求字节经双包 wire parity 测试钉死逐字节一致。结果：

| 配置 | 官方合计（token） | 网关合计（token） | 倍率 |
|---|---|---|---|
| A（裸 diff 无工具） | 270,345 | 195,121 | 0.72×（更省） |
| B（prefetch 预取） | 579,813 | 386,035 | 0.67×（更省） |
| C（全量上下文+工具） | 3,307,877 | 5,500,500 | 1.66× |
| D（工具+稳定前缀） | 958,331 | 2,603,830 | **2.72×** |
| E（D+账本止损） | 1,396,401 | 2,602,453 | 1.86× |
| **合计** | **6,512,767** | **11,287,939** | **1.68~1.73×** |

差异归因（按影响量级，均已排除请求被改写、工具名适配等客户端因素）：

1. **同名模型 id 背后是不同部署版本**：网关侧实为 `deepseek-v4-flash-ga-260731`，多轮工具场景 rounds 1→4、输出 +122%，单轮场景输出收敛。请求字节相同而消耗差 3.3 倍，纯为服务端行为差异。
2. **缓存基础设施差异**：官方即时建立、全前缀命中；网关异步预热 45~90 秒 + 块对齐部分前缀。快速循环场景缓存命中率 84.8% → 40.4%（−44pt）。
3. **usage 字段族差异**：官方报 `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`；网关只报 OpenAI 形态 `prompt_tokens_details.cached_tokens`。
4. **计量噪声**：网关同内容请求 `prompt_tokens` 计数有 ±8% 抖动（官方稳定）；缓存命中按 1024-token 块对齐上报，短前缀近半输入不计命中。

### 1.2 需求分级

- **P0（必须）**：不满足则本系统功能或计量直接受损，阻塞接入。
- **P1（强烈建议）**：不阻塞功能，但显著影响成本与实验指标质量。

## 2. 调用方契约（本系统将如何使用网关）

以下为本系统现状行为，均已在线上验证，网关团队按此设计对接：

| 维度 | 本系统行为 |
|---|---|
| 协议 | OpenAI 兼容 `POST {base}/chat/completions`，`Authorization: Bearer <key>`，**非流式**（`stream:false`，全线无流式调用） |
| 请求体 | JSON，首键 `model`；含 `messages`，可选 `thinking` / `reasoning_effort` / `max_tokens` / `tools` / `tool_choice`；字段序固定（客户端有 golden bytes 冻结测试） |
| 模型 | reviewer 与 judge 可为不同模型（deepseek / qwen / glm / minimax 等自由 id，由实验参数下发，网关须原样透传） |
| 凭据 | key 仅从环境变量读取，绝不落盘、不入库、不进实验记录 |
| usage 消费 | 从每次响应的 `usage` 对象读取计量，双读两族缓存字段（见 M2）；失败重试的已耗 usage 并账 |
| 调用形态 | 每实验单元 1~6+ 次请求，多为同前缀追加（依赖前缀缓存命中） |

## 4. 需求详述

### M1 OpenAI 兼容非流式接口（P0）

**需求**：网关提供 OpenAI 兼容的 `/chat/completions` 端点与 Bearer 鉴权；非流式（`stream:false`）请求完整可用——返回 HTTP 200 与完整 JSON 响应（含 `choices`、`usage`），不强制流式、不强制 SSE。

**依据**：本系统全线非流式，请求字节可审计是实验可复现性的基础（分析报告 §2.1）。

**验收标准**：
1. 以 `stream:false` 发送标准 chat/completions 请求，返回 200，响应体为完整 JSON（非分片）。
2. 响应含 `choices[0].message.content` 与 `usage` 对象。

### M2 usage 字段完整上报（P0）

**需求**：
1. `usage.prompt_tokens` 与 `usage.completion_tokens` 在每次成功响应中必报。
2. 缓存计量至少支持一族字段：
   - DeepSeek 族：`prompt_cache_hit_tokens` + `prompt_cache_miss_tokens`；或
   - OpenAI 族：`prompt_tokens_details.cached_tokens`。
3. 两族同时上报不冲突（客户端双读，DeepSeek 族优先）。
4. **未命中时缓存字段须显式为 0，而非缺省**——客户端须区分「报了 0」（有信息量的记账）与「没报」（无缓存计量能力）。

**依据**：实测网关不报官方字段族，客户端为此做了双读回退适配；若两族全缺，缓存命中率指标静默归零，输出成本指标退化为保守上界（分析报告 §5 归因 3）。

**验收标准**：
1. 任意成功响应含非空 `prompt_tokens`、`completion_tokens`。
2. 构造缓存命中场景（同前缀连发），响应含上述至少一族的缓存字段且取值合理（命中数 ≤ prompt_tokens）。
3. 构造未命中场景（随机前缀），缓存字段存在且为 0。

### M3 请求体原样透传，不改写字节（P0）

**需求**：网关将请求体原样送达后端模型服务：
1. `model` 字段值原样到达，不经别名映射、不改写；
2. `thinking` / `reasoning_effort` / `max_tokens` / `tools` / `tool_choice` 等字段不被剥离、重排或改值。

**依据**：本系统对「同一逻辑请求 → 相同 JSON 字节」有 golden bytes 冻结测试与可重放的请求留痕契约；网关改写请求会破坏可复现性，且曾观测到的 token 消耗差异须能排除请求被改写这一因素（分析报告 §5 排除项）。

**验收标准**：
1. 取本系统一次真实请求的原文（可由 ReviewAgent 团队提供 audit 留痕），经网关重放，网关侧收到的请求体与之逐字节一致（或双方确认语义等价的差异清单，如网关注入的追踪头之外的字段不变）。
2. 请求含 `thinking`/`reasoning_effort` 等非标字段时，模型行为与直连后端一致（不因字段被剥离而退化为非推理调用）。

### M4 function calling 完整往返（P0）

**需求**：
1. 请求 `tools` 数组正常下发；
2. 响应正常返回 `choices[0].message.tool_calls`；
3. 工具结果消息（`role:"tool"` + `tool_call_id`）回传后多轮续接正常；
4. 工具名接受 `^[a-zA-Z0-9_-]+$`（含下划线、连字符）。

**依据**：本系统的评审流程依赖工具循环；历史上因工具名校验规则不兼容导致过 400（点号工具名已客户端下划线化，服务端须接受转换后的名字，分析报告 §5 排除项）。

**验收标准**：
1. 带 `tools` 的请求返回合法 `tool_calls`。
2. 以 `role:"tool"` 消息回传工具结果，续接轮正常产出。
3. 工具名含 `_` / `-` 不被拒绝。

### M5 模型 id 可诊断、不静默路由（P0）

**需求**：
1. 网关提供（或文档披露）可用模型 id 清单；
2. 请求不存在的模型 id 时返回 404 或含 "model not found" 语义的 400，**不得**返回 200，不得静默路由到其他模型。

**依据**：本系统支持实验参数自由下发模型 id；静默路由会直接污染实验数据（模型 id 是实验变量，分析报告 §2.2）。

**验收标准**：
1. 请求一个不存在的模型 id，收到明确错误（非 200），错误信息含可识别的「模型不存在」语义。
2. 错误信息能区分「模型不存在」与「鉴权失败」「配额不足」等其他类别。

### M6 错误语义稳定 + 软错误 usage 回报（P0）

**需求**：
1. 402（余额）/ 429（限流）/ 5xx / 超时 / 响应形状异常等错误的 HTTP 状态码与错误体结构稳定可分类，不随版本漂移；
2. 限流、资源不足等**软错误发生后，若该次调用已产生推理消耗，已耗 usage 须能随错误体回报或经调用日志查询**。

**依据**：本系统对失败重试的已耗 usage 并账（否则重试成本不可见、实验计量失真）；历史上 402 发生在计费前、软错误携带 usage 的场景已由客户端适配（分析报告 §3.1 采集链）。

**验收标准**：
1. 构造限流/配额不足场景，错误码与错误体结构稳定且可分类。
2. 软错误场景下，该次调用的已耗 token 可从错误体或调用日志（M7）中取得。

### M7 调用级账单 / usage 日志（P0）

**需求**：网关侧提供按时间窗 / 调用 / 模型维度聚合的 usage 明细（账单或日志 API），且计费口径（未命中输入 + 输出）与含缓存读口径可区分。

**依据**：客户端只能拿到响应内的 usage；本系统 judge 链等消费者存在逐调用 usage 未落盘的场景，必须有网关侧账单兜底才能对账（分析报告 §7 缺口 2）。

**验收标准**：
1. 能按时间窗查询各模型 token 消耗明细，与客户端侧汇总对得上（误差可解释）。
2. 账单/日志可区分缓存命中与未命中输入的计费差异。

### S1 缓存同步建立，或预热窗口可配置 / 可查询（P1）

**需求**：前缀缓存同步建立（第二次同前缀请求即报命中，官方行为）；若技术上只能异步预热，预热窗口时长需可配置或有文档披露。

**依据**：实测网关异步预热 45~90 秒，快速循环场景（请求间隔小于预热窗）命中率从 84.8% 崩塌至 40.4%，直接改写成本结论（分析报告 §5 归因 2）。

**验收标准**：连续发送同前缀请求，第二次请求即报缓存命中；或实测预热窗口并披露，且窗口可配置。

### S2 缓存命中粒度披露（P1）

**需求**：文档披露前缀缓存的块大小与对齐规则；目标方向为全前缀命中（官方行为）。

**依据**：实测某网关按 1024-token 块对齐上报命中，短前缀场景近半输入不计命中，系统性压低命中率指标（分析报告 §4.4 微观证据）。

**验收标准**：块大小与对齐规则有文档；用同前缀不同截断长度的探针请求实测，命中数与披露规则一致。

### S3 token 计数确定性（P1）

**需求**：同内容请求的 `prompt_tokens` 计数稳定。

**依据**：实测网关同内容请求计数有 ±8% 抖动（官方稳定），直接进入实验指标噪声（分析报告 §5 归因 4）。

**验收标准**：同一请求内容重复 ≥10 次，`prompt_tokens` 计数方差 < 1%。

### S4 reasoning token 单列计量（P1）

**需求**：推理类模型的响应透传 `completion_tokens_details.reasoning_tokens`。

**依据**：DeepSeek 官方将思考并入 `completion_tokens`，glm 网关单独上报但本系统当前未消费——单列后跨推理/非推理模型的输出成本才可解释、可对比（分析报告 §7 缺口 4）。

**验收标准**：推理模型响应含 `reasoning_tokens` 字段且取值合理（≤ completion_tokens）。

### S5 部署版本披露 + 同 id 不换权重（P1）

**需求**：
1. 「模型 id → 实际部署版本/权重版本」作为可查询元数据（接口或文档）；
2. 同名 id 更换部署版本须提前通告（变更通知机制），不得无感切换。

**依据**：实测同名 `deepseek-v4-flash` 在网关侧实为另一部署（ga-260731），多轮工具场景消耗 3.3 倍、行为方向不一致——同名 id 不同部署是网关聚合第三方模型的固有风险，不披露则跨通道对比与成本回归不可归因（分析报告 §5 归因 1，最大影响项）。

**验收标准**：
1. 对任一可用模型 id，能查到其当前部署版本标识。
2. 有变更通告渠道；历史上有换版记录可追溯。

### S6 usage 原文随调用可取（P1）

**需求**：网关提供调用级响应留痕，或至少 usage 原文日志（保留字段族原貌），可按调用/时间窗查询。

**依据**：本系统当前只落请求侧原文、不落响应侧；字段族归因（DeepSeek 族 vs OpenAI 族）依赖客户端回退链推断（分析报告 §7 缺口 3）。

**验收标准**：能查询到指定调用的响应 usage 原始 JSON。

### S7 一网关多模型族路由、口径一致（P1）

**需求**：reviewer 与 judge 的不同模型族（deepseek / qwen / glm / minimax 等）可同网关并存；各模型族的 usage 字段族与计数口径保持一致（或差异文档化）。

**依据**：本系统已实测同网关下 deepseek + qwen + minimax 异构组合（#47）；混布时口径不一致会使跨模型实验不可比（分析报告 §6.2）。

**验收标准**：至少两组异构模型（如一组 deepseek + 一组 qwen）在同一网关下通过端到端冒烟，usage 口径一致或差异已文档化。

## 5. 验收方式与共同工具

1. **冒烟命令**：本系统已内置网关冒烟子命令（`pnpm --filter review-dsh cli smoke`，内部记录 #46），覆盖补全 / 工具调用 / usage 读数 / 错误语义探针，M1/M2/M4/M5 可直接用它验收。网关团队可申请由 ReviewAgent 团队协助执行，或参照其探针逻辑自建等价测试。
2. **wire 重放对比**：M3 由 ReviewAgent 团队提供真实请求留痕（audit wireBody），网关侧比对收到的字节。
3. **cache probe**：S1/S2 的预热窗口与块大小测定，建议作为网关接入验收的标准步骤（分析报告 §7 建议用最小探针对目标网关测定）。
4. **建议验收顺序**：M1 → M4 → M5（功能闭环）→ M2 → M6 → M3（计量与透传）→ M7（对账）→ S 系列。
5. 每条需求的验收结果建议回填本文档 §3 总览表状态列，作为接入放行依据。

## 6. 开放问题与未验证项

1. **流式**：本系统当前全线非流式（M1）。若网关仅提供流式接口，需另行协商 SSE 聚合与 usage 末 chunk 语义——此为未验证能力，不在本版需求内。
2. **对照实验**：官方 vs 网关的大样本对照仅在小样本完成。若网关上游为第三方 provider，建议以「网关 vs 上游原生 API」同型实验固化对照（可选，不阻塞接入）。
3. **并发与配额**：本需求未覆盖网关的并发上限/配额管理，需网关团队另行提供容量说明（本系统实验高峰为多单元并行调用）。
